## 0. Решения, которые нужно принять до старта

Помечены ❗. Пока их нет, кодить можно, а запускаться нельзя.

- ❗ **Юрлицо и эквайринг.** Для приёма карт и СБП нужны ИП или ООО и договор с эквайером (ЮKassa, CloudPayments, Т-Банк и т. п.). Каждый платёж обязан сопровождаться онлайн-чеком по 54-ФЗ: у ЮKassa и CloudPayments для этого есть свои облачные кассы. Подходит ли самозанятость для такой деятельности и как считать НДС, я не знаю наверняка. Это вопрос к бухгалтеру.
- ❗ **Откуда берутся ключи вендоров и как они живут.** Условия OpenAI и Anthropic, насколько я знаю, запрещают перепродавать и передавать доступ к API третьим лицам, а РФ не входит в список поддерживаемых стран. На этом держится вся ниша, и главный операционный риск — бан аккаунта. У тебя мало ключей, поэтому один бан выбивает заметную часть каталога. Отсюда требования к архитектуре: у каждой модели минимум два источника, есть health-check и кэп расходов на каждый ключ (раздел 4).
- ❗ **Где стоит egress.** Вариант по умолчанию: шлюз на VPS в РФ, исходящие запросы к вендорам идут через сервер в ЕС. Можно и всё держать в ЕС, но тогда пропадает аргумент про 152-ФЗ.
- ❗ **Наценка и курс.** Формула в разделе 5; значения задаёшь ты.

## 1. Продукт

**Одной фразой:** один API-ключ и оплата в рублях дают доступ к отобранным моделям (GPT, Claude, Gemini, DeepSeek, Qwen…) через стандартные SDK без VPN.

**Отличие от конкурентов.** Модели у тебя те же, и каталог меньше, поэтому соревноваться количеством (400+ моделей) бессмысленно. Сильные стороны маленького каталога:
- **курация:** 15–30 моделей, у каждой написано, для чего она лучше подходит;
- **стабильность:** у каждой модели есть резервный источник, а статусная страница показывает реальный аптайм;
- **простота:** понятная цена за типичный запрос («≈0,3 ₽ за ответ в чате»), а не только за 1M токенов;
- **ниша:** можно выбрать одну и сделать её сильнее всех, например вайб-кодинг (готовые конфиги для Claude Code, Cursor, Cline) или малый бизнес с документами для юрлиц.

**Аудитории:**
1. Разработчики и инди-хакеры: API, ключи, документация.
2. Вайб-кодеры: пошаговые гайды для IDE и агентов.
3. Бизнес: счёт, договор, ЭДО, общий баланс команды.
4. Обычные пользователи: веб-чат. Это не MVP, этап 2.

## 2. Скоуп

### MVP
- Лендинг, каталог моделей, карточка модели, страница цен.
- Регистрация и вход: email с паролем и magic link; опционально Яндекс ID или Telegram.
- Личный кабинет: баланс, пополнение (карта и СБП), история платежей, API-ключи с лимитами, статистика расходов, лог запросов (только метаданные).
- API-шлюз: OpenAI-совместимые `/v1/chat/completions` (включая стрим), `/v1/models`, `/v1/embeddings`; отдельный `GET /v1/balance`.
- Биллинг: предварительная проверка баланса, списание по `usage`, журнал проводок.
- Админка: пользователи, ручная корректировка баланса, модели и цены, пул вендорских ключей, курс и наценка, платежи.
- Документация: быстрый старт, аутентификация, модели, ошибки, лимиты, стоимость, 3–5 интеграций.
- Юридические страницы: оферта, политика ПДн, согласие на обработку ПДн, условия возврата, реквизиты.
- Письма: подтверждение email, успешное пополнение, низкий баланс.

### Этап 2
- Anthropic Messages API (`/v1/messages`), чтобы Claude Code работал нативно; Responses API.
- Веб-чат и playground в карточке модели.
- Юрлица: выставление счёта, акты, ЭДО.
- Команды: общий баланс, роли, бюджеты участников.
- Изображения, STT и TTS.
- Статусная страница, промокоды, реферальная программа, Telegram-бот.
- Маскирование ПДн (как у ProxyAPI).

### Вне скоупа
Маркетплейс GPU-провайдеров, видео-генерация, desktop-приложение.

|---|---|---|
| Фронт, кабинет и админка | **Next.js (App Router) + TypeScript + Tailwind + shadcn/ui** | SSR для SEO каталога и карточек, один репозиторий |
| БД | **PostgreSQL** | транзакции для денег |
| ORM | Prisma или Drizzle | |

| | вариант B: свой шлюз на Node (Fastify) или Go | полный контроль над форматом ответов и биллингом, но fallback, стриминг, подсчёт токенов и различия протоколов придётся писать и поддерживать самим |
| Платежи | ЮKassa (или CloudPayments / Т-Банк) + чеки 54-ФЗ | |
| Почта | Unisender или Postmark (или любой SMTP) | |
| Деплой | Docker Compose на VPS; позже Kubernetes | |
| Мониторинг | Sentry, Uptime Kuma (он же статусная страница), Grafana и Prometheus по желанию | |

Сначала проверь в актуальной документации LiteLLM (через context7), какие функции входят в бесплатную версию, а какие только в enterprise (SSO, часть логирования и т. п.). По памяти ядро (прокси, ключи, бюджеты, роутинг) бесплатно, но это нужно подтвердить.

### Схема при варианте A

```
                 ┌──────────────── Next.js (сайт, кабинет, админка, /api/*) ─────────────┐
Браузер ────────►│  auth · платежи · ledger · CRUD ключей через LiteLLM Admin API        │
                 └──────────────┬───────────────────────────────▲────────────────────────┘
                                │ создать/обновить ключ,          │ webhook/callback
                                │ max_budget = баланс             │ "запрос стоил X"
                                ▼                                 │
SDK клиента ──► api.{brand}.ru ──► LiteLLM Proxy ── пул ключей ──► egress (ЕС) ──► вендоры
                                   (virtual keys, budgets, fallbacks, cooldown)
```

Правило для денег: **источник правды по балансу — ledger в нашей Postgres**, а бюджет в LiteLLM только его зеркало для enforcement. Каждый запрос стоимостью X порождает одну проводку `debit`. Раз в N минут сверка сравнивает наш ledger с spend-логами LiteLLM и пишет алерт при расхождении.

## 4. Пул вендорских ключей (главное при малом числе ключей)

- Каждый ключ — запись `provider_key`: провайдер, зашифрованный секрет, egress-маршрут, лимиты RPM/TPM вендора, месячный кэп расходов в $, статус (`active`, `cooldown`, `disabled`, `banned`), дата последней ошибки.
- Одна публичная модель (`anthropic/claude-sonnet-…`) может обслуживаться несколькими деплойментами: разные ключи, другой вендор-хостер (Bedrock, Vertex) или реселлер-апстрим.
- **Роутинг:** выбирается наименее загруженный активный ключ. На 429 или 5xx ключ уходит в cooldown и запрос повторяется на следующем. На 401 или 403 ключ получает `disabled` и мне сразу летит алерт в Telegram.
- **Защита ключей от бана:**
  - пауза клиентского ключа после серии ошибок (как у ProxyAPI: 20 ошибок 4xx за минуту → 1 мин → 10 мин → 1 ч → 12 ч);
  - модерационный фильтр на входе, по желанию (OpenAI moderation или своя модель): у вендоров бывают баны за контент;
  - общий RPM и TPM на клиентский ключ по умолчанию; лимиты повышаются после первого пополнения, по тирам.
- **Кэп расходов** на каждый вендорский ключ: при достижении 90% ключ выводится из ротации.
- Если у модели не осталось живых ключей: `503 model_unavailable`, модель в каталоге получает бейдж «временно недоступна».

## 5. Цены и биллинг

### Формула цены
```
цена_₽_за_1M = ceil_to( цена_вендора_$ × курс_ЦБ × (1 + FX_буфер) × (1 + наценка) × (1 + НДС?), шаг_округления )
```
- `FX_буфер` (например 5–10%) страхует от скачков курса. Цены пересчитываются не автоматически каждый день, а кнопкой в админке с предпросмотром изменений.
- Наценку можно задать глобально и переопределить для модели.
- Отдельные цены: `input`, `output`, `cached_input`, `cache_write`, `reasoning` (если вендор считает его отдельно), `per_request` (веб-поиск), `per_image`.
- В каталоге показываем цену за 1M токенов и «≈ стоимость типичного запроса».

### Жизненный цикл запроса
1. Аутентификация ключа (хэш SHA-256 из кэша Redis), проверка статуса, белого списка моделей и IP, лимитов ключа.
2. Предварительная проверка: `оценка = input_tokens × p_in + (max_tokens ?? model.max_output) × p_out`. Если `balance < оценка`, отвечаем **402** `insufficient_balance`. Деньги не резервируем, как ProxyAPI. Параллельные запросы могут увести баланс немного в минус; допустимый минус ограничен настройкой `overdraft_limit`.
3. Проксирование, в том числе SSE-стрима. Для стрима включаем `stream_options.include_usage`, чтобы получить `usage` в конце.
4. Фактическая стоимость по `usage` → транзакция в Postgres: `INSERT ledger(debit)` плюс `UPDATE balance`, с уникальным ключом `request_id` для идемпотентности.
5. Запись в `request_log`: метаданные без текста промптов по умолчанию. Хранение содержимого клиент включает сам, флагом в настройках.
6. Если клиент оборвал стрим, списываем за сгенерированное до обрыва (если usage не пришёл, считаем токены токенайзером).

### Пополнение
- Минимальная сумма (например 100 ₽) и пресеты 300 / 1000 / 5000 ₽.
- Баланс зачисляется **только по вебхуку эквайера** с проверкой подписи и идемпотентностью по `payment_id`, а не по редиректу.
- Чек 54-ФЗ через кассу эквайера. Предмет расчёта — «услуга», признак — «аванс» или «предоплата». Как оформлять, уточни у бухгалтера.
- Возврат неизрасходованного остатка по заявке, в оферте.

provider_key(id, provider, secret_enc, egress, status, monthly_cap_usd, spent_usd_month, cooldown_until, notes)

ledger(id, account_id, type[topup|debit|refund|adjustment|bonus], amount_kopecks, balance_after,

Деньги храним **в копейках, целыми числами**. Цены за токен — в копейках за 1M токенов (BIGINT) или в NUMERIC(18,6), но не во float.

## 7. API (публичный контракт)

- Base URL: `https://api.{brand}.ru/v1`, заголовок `Authorization: Bearer sk-{brand}-…`.
- `POST /v1/chat/completions` — полностью OpenAI-совместимый: stream, tools, response_format, vision.
- `GET /v1/models` — только публичные и доступные модели, в формате OpenAI плюс поле `pricing`.
- `POST /v1/embeddings`.
- `GET /v1/balance` — только если у ключа есть право `can_read_balance`.
- Этап 2: `POST /v1/messages` (Anthropic), `/v1/responses`, `/v1/images/generations`, `/v1/audio/*`.
- Ошибки в формате OpenAI `{error:{message,type,code}}`:
  `401 invalid_api_key`, `402 insufficient_balance`, `403 model_not_allowed`, `404 model_not_found`,
  `429 rate_limited`, `502 upstream_error`, `503 model_unavailable`.
- В каждом ответе заголовок `x-request-id`; по желанию `x-cost-rub`.

## 8. Страницы

**Публичные:** `/` лендинг · `/models` каталог · `/models/[vendor]/[slug]` карточка · `/pricing` · `/docs/*` · `/for-business` · `/vibe-coding` · `/openrouter-alternative` · `/status` · `/legal/offer` · `/legal/privacy` · `/legal/refund` · `/contacts`.

**Кабинет** `/app`: обзор (баланс, расход за 7 и 30 дней, быстрый старт) · `/app/billing` (пополнить, история, документы) · `/app/keys` · `/app/usage` (графики по дням, моделям и ключам, экспорт CSV) · `/app/logs` · `/app/settings` (профиль, уведомления, хранение логов).

**Админка** `/admin`: дашборд (выручка, себестоимость, маржа, активные пользователи, ошибки по провайдерам) · пользователи · платежи · модели и цены · пул ключей · настройки (курс, наценка) · аудит-лог действий админов.

**Каталог:** поиск, фильтры (вендор, модальность, возможности, тир, диапазон цены, контекст), сортировка (популярность, цена, новизна, контекст), переключатель «цена за 1M / за типичный запрос».

**Карточка модели:** ID с кнопкой копирования, описание «для чего хороша», характеристики, таблица цен, возможности (бейджи), примеры кода (Python, Node, cURL, с подставленным ID), статус и аптайм за 7 дней, похожие модели.

## 9. Дизайн

- Свой узнаваемый стиль. Удачные приёмы OpenRouter-подобных сайтов (тёмные акцентные блоки, свечения, градиенты) использовать можно, но без копирования один в один.
- Сначала бренд-платформа: имя, тон (например «инженерный и спокойный»), акцентный цвет, шрифтовая пара (кириллица обязательна: Inter, Manrope, Onest, Golos, JetBrains Mono для кода).
- Дизайн-токены (цвета, радиусы, тени, отступы) в CSS-переменных, светлая и тёмная темы, ориентир контраста WCAG AA.
- Код и ID моделей моноширинным шрифтом с копированием в один клик: для разработчика это главный интерфейс.
- Mobile-first для лендинга и каталога; кабинет адаптивный.

## 10. Безопасность и соответствие

- API-ключ показываем один раз, храним SHA-256 хэш и префикс для отображения.
- Вендорские ключи шифруем (AES-GCM, мастер-ключ в env или KMS). В логи и в браузер они не попадают никогда.
- Вебхуки платежей: проверка подписи или IP эквайера и идемпотентность.
- Rate limit на логин, регистрацию и отправку писем; капча (Yandex SmartCaptcha) на регистрацию.
- 152-ФЗ: уведомление в РКН об обработке ПДн, согласие при регистрации, ПДн граждан РФ хранятся в РФ.
- Все изменения баланса только через ledger. Ручные корректировки только от админа с комментарием, с записью в аудит.
- Бэкапы Postgres ежедневно, с тестом восстановления.

## 11. Метрики

Регистрация → первое пополнение (конверсия), время до первого запроса, ARPU, маржа по моделям (выручка минус себестоимость в $ по курсу), доля ошибок upstream по ключам, аптайм по моделям.
