# Промпты для пошаговой сборки (Claude Code)

Как пользоваться:
1. Создай пустой репозиторий и положи в `docs/` файлы `01-RESEARCH.md` и `02-SPEC.md` (второй переименуй в `SPEC.md`).
2. Каждый этап — отдельная сессия или отдельная ветка. Этапы запускаются по порядку, следующий только после того, как ты проверил результат предыдущего.
3. Этапы 1–2 лучше делать в plan mode: сначала план, потом код.
4. Если по ходу меняется решение, сначала правь `SPEC.md`, потом код.

---

## Этап 0. CLAUDE.md проекта

```
Создай CLAUDE.md в корне репозитория. Это проект {BRAND} — сайт-витрина и API-шлюз
к AI-моделям с оплатой в рублях. Источник правды по требованиям — docs/SPEC.md,
анализ конкурентов — docs/01-RESEARCH.md; прочитай оба.

В CLAUDE.md зафиксируй коротко:
- стек из SPEC §3 и структуру монорепо (apps/web, infra/, docs/);
- правила про деньги из SPEC §5–6: только копейки BIGINT, только ledger, идемпотентность
  по request_id/payment_id, никаких float;
- правила безопасности из SPEC §10;
- команды: dev, test, lint, миграции, docker compose up;
- правило: при расхождении кода и SPEC — остановиться и спросить, а не угадывать.
Не больше 80 строк.
```

## Этап 1. Каркас и инфраструктура

```
По docs/SPEC.md §3 подними каркас:
- Next.js (App Router, TS strict) + Tailwind + shadcn/ui в apps/web;
- Prisma (или Drizzle — предложи, что лучше здесь, и жди моего выбора) + схема из SPEC §6;
- docker-compose: postgres, redis, litellm (с отдельной БД), web;
- .env.example со всеми переменными, без реальных секретов;
- seed: админ, 3 тестовые модели, настройки курса/наценки.
Перед установкой LiteLLM проверь через context7 актуальную документацию: конфиг,
virtual keys, budgets, admin API, callbacks, что бесплатно, а что enterprise.
Выпиши мне найденные ограничения до того, как писать интеграцию.
Критерий готовности: `docker compose up` поднимает всё, миграции применяются, web открывается.
```

## Этап 2. Шлюз и пул ключей

```
Реализуй SPEC §4 и §7 на LiteLLM:
- config: модели из нашей БД → model_list LiteLLM (генерация конфига или загрузка через admin API —
  выбери и обоснуй); несколько деплойментов на одну публичную модель, роутинг, fallbacks,
  cooldown на 429/5xx;
- egress через прокси (переменная HTTPS_PROXY на уровне деплоймента или контейнера);
- при 401/403 от вендора — ключ в disabled + алерт в Telegram (бот-токен из env);
- кэп расходов на provider_key: выводим из ротации на 90%.
Напиши интеграционный тест с фейковым апстримом (мок-сервер OpenAI-формата), который проверяет:
стрим, fallback на второй ключ при 429, 503 когда живых ключей нет.
Не добавляй реальные вендорские ключи в код и тесты.
```

## Этап 3. Биллинг

```
Реализуй SPEC §5 полностью:
- формула цены и пересчёт цен в админке с предпросмотром diff;
- предварительная проверка баланса → 402 insufficient_balance;
- списание по фактическому usage через callback/webhook LiteLLM → наш endpoint
  (подпись общим секретом), одна транзакция: ledger INSERT + balance UPDATE, идемпотентно по request_id;
- синхронизация бюджета LiteLLM-ключа с нашим балансом при каждом изменении баланса;
- job сверки ledger vs spend-логи LiteLLM раз в 10 минут, алерт при расхождении > 1 ₽;
- учёт cached/reasoning токенов и оборванных стримов.
Тесты обязательны: юнит на формулу и расчёт стоимости; конкурентный тест — 50 параллельных списаний
не ломают баланс; повторный callback с тем же request_id не списывает дважды.
```

## Этап 4. Аутентификация и платежи

```
- Регистрация/вход: email+пароль и magic link; подтверждение email; сброс пароля;
  rate limit и Yandex SmartCaptcha на регистрацию; чекбокс согласия на обработку ПДн с датой.
- Пополнение через ЮKassa (SDK/REST, проверь актуальную доку): создание платежа, редирект,
  зачисление ТОЛЬКО по webhook с проверкой, идемпотентность по provider_payment_id,
  чек 54-ФЗ через «Чеки от ЮKassa» (данные чека вынеси в настройки — их уточнит бухгалтер).
- Письма: подтверждение, успешное пополнение, низкий баланс (порог настраивается пользователем).
Сделай платёжного провайдера интерфейсом, чтобы потом добавить CloudPayments/Т-Банк без переписывания.
Тест: webhook пришёл дважды → одно зачисление; webhook с неверной подписью → 401, баланс не меняется.
```

## Этап 5. Личный кабинет

```
Сделай /app по SPEC §8:
- обзор: баланс, расход 7/30 дней, блок «быстрый старт» с curl/Python, где уже подставлен base URL;
- ключи: создать (показать секрет один раз), имя, бюджет, разрешённые модели, IP, право читать баланс,
  отключить/удалить; всё синхронизируется с LiteLLM;
- usage: графики по дням/моделям/ключам, экспорт CSV;
- logs: таблица request_log с фильтрами, без содержимого промптов;
- billing: пополнение, история платежей и проводок;
- settings: профиль, уведомления, флаг хранения содержимого запросов (по умолчанию выкл).
Пустые состояния и ошибки продумать: новый пользователь без баланса должен понимать следующий шаг.
```

## Этап 7. Публичная витрина

```
По SPEC §8 и выбранной дизайн-системе сверстай:

- карточка модели: всё из SPEC §8, примеры кода с подставленным ID, похожие модели;
- /pricing, /for-business, /vibe-coding, /openrouter-alternative;
- SEO: metadata, OpenGraph, sitemap.xml, robots.txt, JSON-LD (Product/Offer для моделей).
Тексты — живые, короткие, без «революционный/инновационный». Lighthouse ≥ 90 на мобильном.
```

## Этап 8. Документация

```
Сделай /docs (MDX): быстрый старт (Python, Node, curl), аутентификация, модели и ID,

```

## Этап 10. Прод-готовность

```
Подготовь запуск:
- деплой: docker compose на VPS, Caddy/Nginx с TLS, отдельные домены {brand}.ru и api.{brand}.ru;
- бэкапы Postgres (ежедневно, 14 дней) + скрипт проверки восстановления;
- Sentry, Uptime Kuma со статус-страницей на /status, алерты в Telegram;
- нагрузочный тест шлюза (k6): 50 RPS стримов на мок-апстриме, p95 overhead шлюза;
- security-чеклист SPEC §10 — пройди по пунктам и отчитайся, что закрыто, что нет;
- юр-страницы: сгенерируй черновики оферты, политики ПДн, возвратов по образцу структуры
  конкурентов, с пометкой «ЧЕРНОВИК — проверить юристу» в начале каждой.
```
